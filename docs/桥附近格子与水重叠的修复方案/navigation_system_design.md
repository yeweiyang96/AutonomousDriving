## 2. 本次新长路线为什么又报同样的错

输入为地图 1：A `(6311.3418, 322.0057)`，B `(2784.6600, -304.4125)`，用户输入高度均未知。日志记录 DLL SHA 为 `fc5191c9d63c4e4b3c917ef4e522ffd6f85c01520df881583f881acbe30d56ed`，`blocked_edges=[]`。

- 道路参考长度：**59.9759 码**。
- 原生完成的局部路线：**486.4916 码**。
- 该次允许上限：**169.9397 码**，对应 `2.5 × 参考长度 + 20`。

末段恢复过程中共出现 14 次此类完成但超长的原生候选。长度判断在偏离和折返指标之前执行，因此日志没有证明这些候选满足道路顺序、没有折返或具有合理几何。不能通过删除长度判断就直接采用它们。

之后规划器回退两次，保留 158 段前缀，从 `(5163.7353, 244.9209, 32.9608)` 向原终点做剩余长段查询，结束于 `node_pool_exhausted`。

|---|---:|---|
| 整条规划展开预算 | 500000 | 所有原生搜索累计的预算 |
| 最后一次查询之前已计费展开 | 27274 | 包含道路引导与恢复过程 |
| 传给最后一次查询的剩余预算 | 472726 | 大于该次实际可用节点池 |
| 最后一次查询展开 | 65535 | 本次终止原因是节点池耗尽 |

| 加载瓦片数据 | 34398588 B，约 32.81 MiB | 低于配置的 384 MiB；不是记录中的瓦片数据内存上限 |
| `output_count` / `output_capacity` | 0 / 65535 | 输出容量和搜索节点池是不同概念；此处诊断没有报告输出截断 |

Detour 的标准 `dtNavMeshQuery::init` 文档将 `maxNodes` 限制为不超过 65535；当前固定源码也使用这一容量。单纯把 `plan_budget` 从 50 万提高到更多，并不会扩大这一池。`0x40000020` 包含 `DT_SUCCESS` 与 `DT_OUT_OF_NODES`，不能仅检查 success 位就宣称已到达终点。[P1][P2]

**本次触发的是现有道路跟随阶段的局部长度约束。** 最终 `remaining_native_fallback_quality` 没有运行，因为剩余长段原生查询并未完成。不能把这次失败归因于新增的“完整 fallback 成功后的质量检查”。

本次审计根据已知 v1/v2 控制流重建出：76 次 fallback 前查询、1 次最终 fallback；5 条 trace 是缓存候选重查，不重复计费。去重后的 27274 次展开与预算检查点完全一致。**77 是控制流重建值，不是本次捕获的逐次 DLL 调用录像。**

## 3. 应固定的三条系统规则

### 3.1 “已审核道路”是路线偏好，还需要当前三维网格的通行验证

二维道路审核不能自动证明桥面高度、相邻表面连接、水陆类别和当前角色净空都正确。建议保留两类状态：人工审核状态，以及绑定具体导航数据和角色参数的通行验证状态。更新瓦片时只使依赖它的验证记录失效，不能把人工审核历史一并丢掉。

用户选“优先已审核道路”时，应优先在有效道路连接上前进。必须离开道路时，记录离开原因、临时走廊、重新接回的位置和道路进度；完整路线应明确显示偏离，避免在失败后无解释地改走大绕路。

禁行记录也应保留原意和来源。旧 polygon ref 不能盲目套到新网格；应根据依赖瓦片摘要、物理位置、方向和模式重新验证。无法迁移的记录标为待重新验证，不能静默当成“现在可以通行”。

### 3.2 拒绝一条局部候选，不等于当前区域不连通

`excessive_detour` 表示候选不满足当前长度偏好；`RESOURCE_LIMIT` 表示查询尚未判定；只有在完整声明的图范围、过滤器和边界条件下，才可以给出有范围的不可达结论。

同一连通分量只证明存在图路径，不保证短路线、不保证满足道路策略。相反，缺少邻接瓦片的局部图断开，也不能证明全地图断开。Westfall 的局部失败和全加载范围内长绕路正是这一差异的实例。

### 3.3 规划成功、数据正确、设备能执行分别验收

路线必须连续到达指定终点表面，经过的类别、转换与数据版本均合法，才能返回完整规划成功。真实控制器还要能确认移动模式、观察实际角色状态并执行相应动作。桥下水面与桥上终点的 XY 相同，也不能互相代替。

## 4. 公共生成修复：从单瓦片安装转为一个可追溯版本

近期统一候选为 **保留较高 span 顶面 area 的修复 + 显式 Monotone 分区**。两处独立桥上，单独应用其中一项都没有恢复预期的直接桥路；组合才通过。保持已验证的角色半径、身高、爬升、坡度、cell 参数与液体输入，不靠缩小角色或把所有 water 改成 ground 取得通过。

修复进入公共 Recast 和共享 TileBuilder，依据几何规则作用于所有位置。候选不是全图已验证版本，发布前要覆盖窄桥、楼层、坡道、洞穴、岸线、危险液体及跨瓦片接缝等不同结构。附录保留已验证的候选 patch，未提供一键替换生产数据的安装器。

现有源码还暴露了三类会让“重建过了但问题仍在”反复出现的行为：

1. **隐式算法回退。** 指定算法失败后，`TileBuilder::buildMoveMapTile` 在特定条件下调用 Layers。新 profile 要记录每个 subtile 实际采用的算法；未声明回退阻止发布。
2. **小块失败后继续。** compact、erosion、region、contour 等阶段存在失败后 `continue` 的分支。必须记录所有预期 subtile 的终态，区分“源输入确实为空”和“计算失败”；进程退出 0 不是完整性证明。
3. **旧产物被缓存复用。** `MapTileBuilder::shouldSkipTile` 使用已有版本、文件存在与修改时间，特定 stat 失败也可能跳过。换算法后应使用新目录与内容摘要缓存，防止旧瓦片获得新版本名称。正常 debug 基类分支不会缓存跳过，不把它误描述为所有 debug 重放都无效。

建议流水线为：固定源数据和工具摘要 → 候选目录批量生成 → 完整性与语义检查 → 真实加载后的连接与路线检查 → Windows DLL 验收 → 切换一个 manifest/pointer。查询固定自己的版本快照；更新 DLL 和 Python 时还需兼容性协商，多个独立文件替换不自动组成事务。

统一扫描按生成版本组织全部已审核道路、跨水区域、层叠表面和边界案例。缺少原始数据的区域在汇总报告中明确列出；不要求用户继续为每座桥选择一套专用采集命令。

## 5. 规划改造：道路进度、上层连接图和局部精细查询

建议采用“道路/区域/门户的上层图 + 有界局部 Detour 查询”。上层边必须对应真实相邻表面或经验证的连接，不按距离任意连线。

对本次这类情况，保留原生完成但质量未接受的候选及其证据，尝试连接更靠前、确实可达的道路位置，并评价整个接回段。只有完整连续、层身份正确、道路顺序合理且总质量符合策略的候选才可接入。一个超长候选被拒绝后，直接把全部剩余路程交给一次细网格搜索，会把局部问题扩大为节点池问题。

防折返要结合道路有向进度与走廊身份，不只比较两点距离。不同高度的相同 XY 不算到达；桥面和桥下的投影重叠不等于连通。Detour 的表面 raycast 忽略终点的竖直分量，因此它本身也不能证明已经从下层走到上层。[P1]

规划预算继续累计所有真实查询；缓存重查只记录决定，不重复计费。回滚前缀不能返还已经花掉的搜索成本。分层查询复用节点池并不免除总预算，也不能通过未经验证的直线拼接绕过可走性检查。

建议对外区分以下失败原因：

| 结果 | 可向用户说明的内容 |
|---|---|
| `ENDPOINT_NO_SURFACE` / `AMBIGUOUS_SURFACE` | 指定点无对应合法表面，或桥上桥下等多层尚未确定 |
| `DATA_INCOMPLETE` | 所需地图、瓦片或语义资料未完整覆盖 |
| `NO_ROUTE_IN_VERIFIED_SCOPE` | 在报告声明的完整范围和通行规则内不可达 |
| `ROAD_POLICY_UNSATISFIED` | 存在已计算候选，但未满足所选道路策略 |
| `SEARCH_NODE_POOL_EXHAUSTED` | 某次原生查询的节点容量耗尽，未判定全局不可达 |
| `PLAN_BUDGET_EXHAUSTED` / `DATA_MEMORY_LIMIT` | 分别是总计算预算或加载内存上限 |
| `OUTPUT_TRUNCATED` | 输出被截断，不能作完整路线执行 |
| `MODE_TRANSITION_UNVERIFIED` | 缺少可执行的入水、上岸或模式转换依据 |

这些是拟采用的语义分类；本次没有替换现有 UI 错误文案。

## 6. 游泳 V1：可设计为稳定能力，但需要水陆分层

### 6.1 默认策略

选择 **WALK_PREFERRED**：优先已验证的道路和桥。用户允许游泳且存在证据完整的水面及上下岸连接时，才评估混合路线。若步行查询只是资源受限，继续标记“步行是否可达未判定”，不能为了启动游泳而把它改写成不可达。

V1 支持地面步行、水面游泳和缓坡上下岸；不把潜水、跳桥落水或攀爬陡岸包含在首版能力里。这是有限而可验证的实现范围。

### 6.2 现有 `water:false` 不能用作开关

固定生成源码默认保留液体几何，实际瓦片也含 water 类面。`manifest.settings.water:false` 没有被当前 loader 用来删除液体或设置查询过滤。当前 DLL 的步行 filter 为 include `0x11`、exclude `0x0e`，而执行器遇到 `SWIMMING` 会停止。

仅往 include 加 `NAV_WATER` 仍会被 exclude 排除；Detour 官方过滤定义明确这一点。[P3] 即使同时改两组 mask，也没有解决上下岸、角色状态、液体危险或误标桥面问题。

今后的清单应分别声明“是否生成液体几何”“允许哪些规划模式”“哪些模式已经通过执行验收”。这些是新契约，不是往旧 JSON 添加三个字段就完成支持。

### 6.3 数据与路线需要的最小结构

| 部分 | 必需内容 | 解决的问题 |
|---|---|---|
| 表面身份 | tile 内容摘要、层、polygon、真实物理类别、来源证据、允许模式 | 区分桥面、水面、水底；识别 water 误标，保留多层目标 |
| 液体语义 | 原始液体类别、水体、液面、所需浸入空间或水深证据、净空与危险/未知覆盖 | 现有 mmtile 粗分类不足，不能把所有 water 当可游 |
| 入水连接 | 有方向的坡岸走廊、支撑/碰撞、能力要求与验证记录 | 能下水不自动代表可以返回岸上 |
| 出水连接 | 独立验证坡度、台阶、落脚面及后续 WALK 连通性 | 避免到达陡岸、孤岛或反复上下水 |
| 有类型路线 | WALK / ENTER_WATER / SWIM_SURFACE / EXIT_WATER、表面和连接 ID、版本及验证状态 | 平滑不能跳过岸口；控制器知道正在执行哪种移动 |

现有生成流程可能舍弃被液体覆盖的底面，并合并 Water/Ocean 等类别。因此不能保证从最终网格反推真实水深；应在统一生成流程中保留液体与碰撞来源 sidecar。已知“solid 被误标 water”的区域必须进入数据诊断，不能被游泳功能自动吞掉。

### 6.4 接口与执行

保留旧步行 ABI，新增带版本、结构大小及能力协商的表面查询、转换查询、规划和路线验证接口。新 Python 必须明确检查加载 DLL 能力，避免再次出现已编译新版、manifest 却加载旧 DLL 的情况。

执行状态为 `WALK → ENTER_WATER → SWIM_SURFACE → EXIT_WATER → WALK`。转换失败暂停该方向，避免持续来回折返。步行中意外落水仍是异常；只有在已验证的入水段内才允许计划中的泳态转换。

当前代码已经有 `SWIMMING` 位，租约输入协议也能表示多键，这是可用基础。但现有 Runtime 实际仍走单键发送，runtime/controller 都有泳态停止逻辑；现有资料还没有证明实时泳态、水面保持和所需按键组合已经可靠。**计划中的水面高度是几何预测，不能填进遥测冒充实际角色高度。**

因此交付顺序是：先实现和验证带模式的混合路线预览，再对现有遥测、按键绑定和设备能力做有限范围执行验收。泳速、转向与上下水确认要独立校准。
