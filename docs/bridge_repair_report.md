## 3. A 端：桥板底面覆盖了桥顶的可行走标记

在栅格 `(379,243)` 的逐三角形原生追踪中：

| 插入的几何 | 合并后的跨度 `[最低格, 最高格, area]` |
|---|---|
| 原地形 | `[51,53,11]` |
| 平坦桥顶 | `[51,54,11]` |
| 随后插入的向下桥底 | **`[50,54,0]`** |

桥顶最高位置仍是 54，却从可行走的 area 11 变成不可行走的 area 0。固定版本的 `RecastRasterization.cpp::addSpan` 在跨度顶面相差超过原阈值时，没有正确继承实际较高顶面的属性。

采用的修正保留原有近高度合并规则，并补上较高顶面的属性继承：

```cpp
if (rcAbs((int)s->smax - (int)cur->smax) <= flagMergeThr)
    s->area = rcMax(s->area, cur->area);
else if (cur->smax > s->smax)
    s->area = cur->area;
```

这两行同时处理了相反的错误情形：较低的可走地面后插入时，不应把已有的较高障碍物改成可走。7 个实际 `rcAddSpan` 对照案例全部通过，包括高障碍和低地面的正反插入顺序、桥顶与底面、以及上下液体/地面标签。

这项验证针对所述顶面合并规则；不声称任意多次带阈值合并都具有完全的顺序无关性。

## 4. B 端：轮廓到多边形转换时，部分地面被标成水面

固定 `Layers` 分区下，桥头附近 12 个连续栅格，在紧凑高度场、原始轮廓和简化轮廓中均仍属于 ground。它们延伸到内部子瓦片边界 `west = -1472`。

最终覆盖这些位置的多边形 517、519 却带有 **water area 9**。因此，当前只允许地面行走的查询过滤器会排除这段连接。

**已确认丢失发生在地面轮廓到最终多边形之间。** 源码中的混合区域和边界顶点重三角化提供了对应机制，但未逐调用跟踪 `removeVertex`，不把细到某次顶点移除的归因表述为已证实。

此地块使用生成器已有的 `--partition monotone` 选项，可保留这段地面连接。组合修复保持其余生成参数不变。

## 5. 因果对照与最终路线

C 表示桥中央。查询使用原项目的 `bridge.cpp` 和相同 Detour 版本编译的本机原生库；ground filter 为 include `0x11`、exclude `0x0e`，不允许 off-mesh。

| 对照 | 结果 |
|---|---|
| 原始网格 | 初始 9 个地块中 A→B 无完整路线；扩大到已记录的 49 个地块后耗尽 65,535 个查询节点 |
| 只修较高顶面的 area 继承 | A→C 成功，7 次展开；C→B 仍无路线 |
| 只使用 Monotone | C→B 可达；A→B 约 151.1 码，绕行到北侧，未修复直接上桥通路 |
| **两项组合** | **A→B 约 41.07174 码、19 次展开；B→A 约 41.07165 码、25 次展开** |

最终双向验证只加载原始第一阶段的 9 个地块，仅替换目标地块。起终点水平坐标保持原值；高度来自对应导航表面。路径包含 13 个输出点。与原始 A–B 水平直距约 40.69 码相比，这是直接过桥路线。

## 6. 交付与安装边界

`apply_bridge_fix.py` 内含已经验证的地块。它会先核对当前文件和配置，再使用用户电脑上的现有 Windows DLL 对候选执行双向查询；通过后才备份并原子更新目标地块索引。原地块文件保留，修复有单独的来源记录与回滚入口。

候选大小：888,768 字节。SHA-256：

```text
74dd28d4d559518bca84b678ac3fb3ccd5ba294c8ab65bebcede927acc46df1c
```

该脚本交付的是这一个已验证地块的数据修复。它会保存源码补丁及生成说明，**不会自动修改或编译用户的 WSL 生成器**。未来重新生成该地块时，需要保留较高顶面属性修正和 Monotone 分区选择，否则原始生成设置仍可能再次产出旧问题。

地块的多边形编号会随修复改变，因此脚本按原项目的算法更新导航包 `identity`。**绑定旧导航包 identity 的禁行边记录将不再匹配新导航包**；脚本不会删除这些记录，也不会把旧多边形编号强行套用到新网格。其他地块的文件与索引条目保持原样。

安装器另经 8 项隔离检查，覆盖实际固定版本的 Linux 原生接口、精确备份、未知字段保留、旧文件不变、重复运行、回滚、拒绝无关修改，以及原生失败或清单替换失败时不切换。清单更新采用写入临时文件后再次比较原始字节，再原子替换的方式；这是一种乐观并发检查，不是操作系统提供的原子比较交换。

把 `apply_bridge_fix.py` 放到项目的 `tools` 目录后，运行下列命令。显式指定项目目录，因此不要求 PowerShell 当前位于项目根目录。

```powershell
& 'D:\wangzekun\Documents\AutonomousDriving\.venv\Scripts\python.exe' 'D:\wangzekun\Documents\AutonomousDriving\tools\apply_bridge_fix.py' --project-root 'D:\wangzekun\Documents\AutonomousDriving'
```

启动时会立即输出进度，完整报告保存到项目的 `runtime\bridge-fix-reports`。首次成功时显示“修复已安装且双向原生验证通过。”需要恢复时，在同一命令后加 `--rollback`；回滚仅接受当前清单与本次修复保存的安装后清单完全一致的情况，防止覆盖后续修改。

本机验证已覆盖原生路径、修复前后对照和源码合并语义；没有在这里直接运行用户的 Windows 进程，也没有验证实际游戏角色的运动。安装脚本的本机 Windows DLL 检查是数据切换前的最后一道验证。
